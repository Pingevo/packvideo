## 0. สรุปสิ่งที่เปลี่ยนจากเอกสารออกแบบ

ตรวจโค้ด `sellcenter` แล้วพบข้อเท็จจริง 3 ข้อที่**ขัดกับสมมติฐานเดิม** และเปลี่ยนสเปคจริง

### 0.1 ⛔ แพลตฟอร์มจำกัดวิดีโอที่ 60 วินาที / 30 MB — ไม่ใช่ตัวเลขที่เราเลือกเอง

[api/services/RefundCaseActionService.js:987](../../sellcenter/api/services/RefundCaseActionService.js)
บันทึกลิมิตจริงที่อ่านจากหน้า Shopee Seller Centre ไว้แล้ว:

```js
var PROOF_LIMITS = { description: 256, files_per_set: 3, image_mb: 10, video_mb: 30, video_sec: 60 };
// ไฟล์ที่รับ: MP4 MOV JPG JPEG PNG
```

เอกสารออกแบบเลือก 60 วินาทีจาก**การคำนวณพื้นที่ดิสก์** ซึ่งบังเอิญตรงกัน แต่ 60 วินาที
เป็น **เพดานแข็งของแพลตฟอร์ม** ไม่ใช่ตัวแปรที่เราปรับได้ ต่อให้ซื้อดิสก์ใหญ่ขึ้นก็ยังส่งเกิน 60 วิ ไม่ได้

**ผล:** เมื่อรวมกับการตัดสินใจว่า "อัดต่อไปเรื่อยๆ จนกว่าจะสแกนปิด" (§FR-1.6)
→ ระบบต้องแยก **ไฟล์เก็บ (ยาวเท่าไรก็ได้)** ออกจาก **ไฟล์ส่ง (≤60 วิ ≤30 MB)** ดู §FR-5

### 0.2 ⛔ วิดีโอส่งผ่าน Open API ไม่ได้ทุกแพลตฟอร์ม

| แพลตฟอร์ม | วิดีโอ | อ้างอิง |
|---|---|---|
| Shopee | ตารางพารามิเตอร์ `upload_proof` **ไม่มีช่องวิดีโอ** — โค้ดเดาโครงสร้าง `body.video` ไว้แต่ยัง **ไม่เคยยิงผ่าน** | [RefundCaseActionService.js:1019](../../sellcenter/api/services/RefundCaseActionService.js) |
| TikTok | Seller Center อัปวิดีโอได้ แต่ Open API ส่งไม่ได้ → หน้าจอแสดงเป็นข้อความบอกให้ไปทำเอง (`submittable: kind !== 'video'`) | [RefundCaseActionService.js:87,147](../../sellcenter/api/services/RefundCaseActionService.js) |
| Lazada | ส่งได้**เฉพาะเคส `REFUND`** ผ่าน `video_info_list` และ **ต้องมีลิงก์รูปปก (cover) คู่กันเสมอ** · เคส `RETURN` ไม่มีช่องวิดีโอเลย | `VideoSupport()` [:2037](../../sellcenter/api/services/RefundCaseActionService.js) |

**ผล 2 ข้อ:**
- การดาวน์โหลดไฟล์ไปอัปมือเป็น **เส้นทางหลัก** ไม่ใช่ทางสำรอง → §FR-5.1 เป็น must
- Lazada REFUND ต้องการ **URL วิดีโอ + URL รูปปก** → ระบบต้องผลิตรูปปกจากคลิปให้ด้วย §FR-5.4

### 0.3 ⛔ "แพลตฟอร์มไม่รับรูปนิ่ง" — ไม่จริง บางเคส**บังคับ**ต้องมีรูปนิ่ง

เอกสารออกแบบ §3 ตัดตัวเลือก D (snapshot) ทิ้งด้วยเหตุผลว่าแพลตฟอร์มไม่รับ แต่ชุดหลักฐานจริงของ TikTok
([RefundCaseActionService.js:94,108](../../sellcenter/api/services/RefundCaseActionService.js)) ระบุว่า:

> `{ requirement: 'หลักฐานการแพ็คสินค้าก่อนจัดส่ง', kind: 'image', max: 6, is_required: true }`

คือ **รูปนิ่งของการแพ็คเป็นหลักฐานที่บังคับ** ในเคส "ผลิตภัณฑ์ไม่ใช่ตัวที่ส่งไป" และ "ชิ้นส่วนหายไป"
ข้อสรุปเดิมถูกเฉพาะประเด็น "รูปนิ่งอย่างเดียวไม่พอ" — แต่ไม่ได้แปลว่าไม่ต้องมี

**ผล:** วิดีโอยังเป็นตัวหลักตามเดิม แต่เพิ่มความต้องการ "ดึงเฟรมนิ่งจากคลิปได้" §FR-5.3
ซึ่งได้มาแทบฟรีเพราะต้องแตะไฟล์อยู่แล้วตอน export

## 1. เป้าหมายและตัวชี้วัดความสำเร็จ

### 1.1 เป้าหมายทางธุรกิจ

| # | เป้าหมาย | วัดจาก |
|---|---|---|
| G1 | ชนะเคสที่ลูกค้าอ้างของไม่ครบ/ผิดรุ่น ได้มากขึ้น | อัตราชนะเคสประเภทนี้ ก่อน vs หลัง |
| G2 | เคลมกับขนส่งได้เมื่อของหาย/เสียหายระหว่างส่ง | จำนวนเคลมที่ยื่นได้ / ยอดเงินที่ได้คืน |
| G3 | ดักการแปะใบปะหน้าผิดกล่องตั้งแต่ที่โต๊ะ | จำนวนครั้งที่ระบบเตือน (ปัจจุบันไม่มีอะไรดักเลย) |
| G4 | รู้ว่าออเดอร์ไหนแพ็คที่โต๊ะไหน โดยใคร | ปัจจุบันไม่มีข้อมูลนี้เลย |

### 1.2 ไม่ใช่เป้าหมาย (Non-goals)

- ไม่ใช่ระบบ CCTV รักษาความปลอดภัยของคลัง (เป็นงบและระบบคนละก้อน)
- ไม่ใช่ระบบวัด productivity รายคนแบบละเอียด (ได้ข้อมูลมาบ้างแต่ไม่ใช่วัตถุประสงค์ที่แจ้ง PDPA)
- ไม่ตรวจสอบว่าของในกล่องถูกต้องอัตโนมัติ (ไม่มี CV/AI)
- ไม่แทนที่การผูก IMEI ที่มีอยู่

## 2. ผู้ใช้งาน (Actors)

| Actor | คือใคร | เข้าถึงอะไร |
|---|---|---|
| **A1 พนักงานแพ็ค** | ประจำโต๊ะ 1 คน/โต๊ะ 6+ โต๊ะ ไม่ใช่สายเทคนิค | หน้าต่างอัดของโต๊ะตัวเอง (พรีวิว + สถานะ) เท่านั้น · ไม่เห็นคลิปย้อนหลัง |
| **A2 หัวหน้าคลัง** | ดูแลหน้างาน | สถานะทุกโต๊ะแบบเรียลไทม์ · รายงานความสมบูรณ์รายคน/รายโต๊ะ |
| **A3 ทีม CS/เคลม** | ผู้ใช้หลักของระบบ ใช้สู้เคส | ค้นหา ดู ดาวน์โหลด ส่งออก สร้างลิงก์ pin ทุกคลิป |
| **A4 ผู้ดูแลระบบ / IT** | 1–2 คน | ตั้ง `station_id` · token · retention · alert · สุขภาพระบบ |
| **A5 ผู้รับภายนอก** | ลูกค้า / เจ้าหน้าที่แพลตฟอร์ม / เจ้าหน้าที่ขนส่ง | **ไม่มีบัญชี** ดูได้ผ่านลิงก์ที่ A3 สร้างให้เท่านั้น |

> A5 เป็น actor ใหม่ที่เอกสารออกแบบไม่มี — เป็นตัวที่สร้างความต้องการด้านความปลอดภัย
> และ PDPA มากที่สุด เพราะข้อมูลออกนอกองค์กร

## 3. ความต้องการเชิงหน้าที่ (Functional Requirements)

### FR-1 การบันทึก

| # | ความต้องการ | ระดับ |
|---|---|---|
| FR-1.1 | เริ่มอัดเมื่อพนักงานกด Enter หลังสแกน IMEI (ก่อนรู้ผลจาก API) | **must** |
| FR-1.2 | ยืนยัน (COMMIT) หรือทิ้งคลิป (ABORT) เมื่อ API ตอบ ตามตารางผลลัพธ์ 6 ทาง | **must** |
| FR-1.3 | ผูก `tracking_no` เข้ากับคลิปเมื่อหน้าใบปะหน้าเรนเดอร์ | **must** |
| FR-1.4 | หยุดอัดเมื่อสแกนบาร์โค้ด tracking บนกล่องที่แปะแล้ว และตรงกับที่จำไว้ → `verified` | **must** |
| FR-1.5 | เตือนทันทีเมื่อสแกน tracking แล้ว**ไม่ตรง** — "ใบปะหน้าไม่ตรงกับออเดอร์ที่กำลังแพ็ค" | **must** |
| FR-1.6 | **ไม่จำกัดความยาวคลิปที่ค่าคงที่** — อัดต่อจนกว่าจะมีเหตุการณ์ปิด (ตัดสินใจแล้ว) | **must** |
| FR-1.7 | มีเพดานความปลอดภัย **สองชั้น** ตีตรา `timeout` ทั้งคู่ — (ก) ไม่มีเหตุการณ์ใดๆ 4 นาที (กล้องหยุด/หน้าต่างปิด) · (ข) อัดเกิน `CLIP_MAX_MINUTES` นับจากเริ่ม (กล้องยังส่งอยู่แต่ไม่มีการสแกนปิด — ชั้น ก จับไม่ได้เพราะชิ้นวิดีโอรีเซ็ตตัวจับเวลา) | **must** |
| FR-1.8 | ปิดคลิปเก่าเป็น `unverified` เมื่อมีการสแกน IMEI ตัวใหม่ทับ | **must** |
| FR-1.9 | ปิดคลิปค้างทั้งหมดเป็น `unverified` เมื่อปิดหน้าต่างอัด / หมดกะ | **must** |
| FR-1.10 | **ปิดคลิปด้วยมือได้** (ปุ่มบนหน้าต่างอัด) กรณีบาร์โค้ดใบปะหน้าสแกนไม่ติด — ตีตรา `manual_stop` แยกจาก `unverified` | **must** |
| FR-1.11 | ไม่บันทึกเสียงในทุกกรณี — ไม่มีสวิตช์ให้เปิด | **must** |
| FR-1.12 | อัปโหลดคลิปแบบไม่บล็อกงานแพ็ค · มีคิวในเครื่อง · อัปซ้ำอัตโนมัติเมื่อเน็ตสะดุด | **must** |
| FR-1.13 | แสดงจำนวนคลิปในคิวรออัปโหลดบนหน้าต่างอัดตลอดเวลา | **must** |

**เหตุผล FR-1.10:** ถ้า STOP มีทางเดียวคือสแกนบาร์โค้ด แล้วขนส่งบางเจ้าพิมพ์บาร์โค้ดไม่ติด
หรือใบยับ พนักงานจะปิดคลิปไม่ได้เลย → ทุกคลิปกลายเป็น `unverified` และตัวชี้วัดวินัยหน้างานพัง
ทั้งที่ปัญหาอยู่ที่เครื่องพิมพ์ `manual_stop` ต้องแยกสถานะเพื่อไม่ให้ตัวเลขปนกัน

### FR-2 การผูกข้อมูลและความครบถ้วน

| # | ความต้องการ | ระดับ |
|---|---|---|
| FR-2.1 | ทุกคลิปต้องผูกกับ `ordersn`, `tracking_no`, `imei[]`, ผู้ใช้ที่ล็อกอิน, `station_id`, เวลาเริ่ม–จบ | **must** |
| FR-2.2 | 1 ออเดอร์ = 1 คลิป แม้สแกน IMEI หลายชิ้น (อัดต่อเนื่อง ไม่แยกไฟล์) | **must** |
| FR-2.3 | **ครอบคลุม 100% ของออเดอร์ที่พิมพ์ใบปะหน้า** — ยืนยันแล้วว่าทุกออเดอร์ผ่าน `/shopee/imei` | **must** |
| FR-2.4 | ตรวจจับและรายงานออเดอร์ที่พิมพ์ใบปะหน้าแล้วแต่ไม่มีคลิป ภายใน 24 ชม. | **must** |
| FR-2.5 | ค่าที่ยังไม่รู้ตอนเริ่มอัด (`ordersn`, `tracking_no`) ต้องเติมย้อนหลังเข้าคลิปเดิมได้ | **must** |
| FR-2.6 | คลิปที่ ABORT ต้องถูกลบจริง ไม่ค้างเป็นขยะบนดิสก์ | **must** |

**เหตุผล FR-2.4:** เอกสารออกแบบเตือนไว้เองว่า `hook.js` เกาะกับ DOM เดิม (`#txt_imei`, `arr_tracking`)
ถ้ามีคนแก้หน้าเดิม hook จะพังเงียบๆ — ไม่มี error ไม่มีใครรู้ จนวันที่ต้องใช้คลิปแล้วไม่มี
ตัวเลข "ออเดอร์ที่ไม่มีคลิป" คือ health check ที่ต้องมีตั้งแต่วันแรก ไม่ใช่ทีหลัง

### FR-3 การจัดเก็บและ retention

| # | ความต้องการ | ระดับ |
|---|---|---|
| FR-3.1 | เก็บคลิปทั่วไป **30 วัน** แล้วลบอัตโนมัติ | **must** |
| FR-3.2 | คลิปที่ถูก pin ไม่ถูกลบตาม retention ไม่ว่าอายุเท่าไร | **must** |
| FR-3.3 | เก็บบนดิสก์ที่แยกจาก filestore/mongo ของระบบเดิม | **must** |
| FR-3.4 | แจ้งเตือนเมื่อดิสก์ถึง 75% ผ่านช่องทางที่ระบบเดิมใช้อยู่ (Telegram) | **must** |
| FR-3.5 | หยุดบันทึกเมื่อดิสก์ถึง 90% **แต่ไม่หยุดงานแพ็ค** — แสดงสถานะแดงชัดเจน | **must** |
| FR-3.6 | สำรองคลิปที่ pin ไว้นอกดิสก์ลูกหลัก | **must** |
| FR-3.7 | เปลี่ยนค่า retention ได้โดยไม่ต้อง deploy | should |
| FR-3.8 | รายงานพื้นที่คงเหลือ + จำนวนวันที่เก็บได้จริงตามอัตราปัจจุบัน | should |

### FR-4 การค้นหาและเข้าถึง (A3 ทีม CS)

| # | ความต้องการ | ระดับ |
|---|---|---|
| FR-4.1 | ค้นคลิปด้วย `ordersn` | **must** |
| FR-4.2 | ค้นคลิปด้วย `tracking_no` | **must** |
| FR-4.3 | ค้นคลิปด้วย IMEI | **must** |
| FR-4.4 | เข้าถึงคลิปได้จากหน้าเคสของ RefundCases โดยตรง ไม่ต้องคัดลอกเลขไปค้นอีกระบบ | **must** |
| FR-4.5 | เล่นคลิปในเบราว์เซอร์ได้ เลื่อนไปกลางคลิปได้ (ไม่ต้องโหลดทั้งไฟล์ก่อน) | **must** |
| FR-4.6 | เห็นสถานะคลิป (`verified` / `unverified` / `manual_stop` / `timeout`) ก่อนเปิดดู | **must** |
| FR-4.7 | ค้นด้วยช่วงวันที่ + โต๊ะ + พนักงาน (สำหรับ A2 ตรวจสอบภายใน) | should |
| FR-4.8 | ถ้าคลิปถูกลบไปแล้วตาม retention ต้องบอกว่า "เคยมี แต่ลบเมื่อ …" ไม่ใช่ "ไม่พบ" | **must** |

**เหตุผล FR-4.8:** "ไม่พบ" ทำให้ CS เข้าใจผิดว่าระบบพัง/ไม่ได้อัด แล้วไปตามหาคนผิด
ทั้งที่เป็นพฤติกรรมปกติของ retention

### FR-5 การส่งออกหลักฐาน ← ส่วนที่เอกสารออกแบบไม่มีเลย

| # | ความต้องการ | ระดับ |
|---|---|---|
| FR-5.1 | ดาวน์โหลดคลิปเป็นไฟล์ **MP4 (H.264)** เพื่อนำไปอัปโหลดเข้า Seller Center ด้วยมือ | **must** |
| FR-5.2 | ไฟล์ที่ดาวน์โหลดต้องผ่านเงื่อนไขแพลตฟอร์ม: **≤ 60 วินาที และ ≤ 30 MB** | **must** |
| FR-5.3 | ดึงเฟรมนิ่งจากคลิปเป็น JPG/PNG **≤ 10 MB** ได้สูงสุด 6 รูป (สำหรับชุดหลักฐาน `kind:'image'` ของ TikTok) | **must** |
| FR-5.4 | ผลิต **รูปปก (cover)** พร้อม URL สำหรับเคส Lazada `REFUND` ที่บังคับต้องมีคู่กับวิดีโอ | **must** |
| FR-5.5 | เมื่อคลิปยาวเกิน 60 วินาที ต้องให้ CS **เลือกช่วง 60 วินาทีที่ต้องการส่ง** ได้ — ต้องเป็นช่วง**ต่อเนื่องช่วงเดียว** ห้ามต่อหลายช่วง | **must** |
| FR-5.6 | ระบบเสนอช่วง 60 วินาทีเริ่มต้นให้อัตโนมัติ (ช่วงที่ครอบคลุมตั้งแต่ปิดกล่องถึงสแกน tracking) | should |

| FR-5.9 | สร้างลิงก์ให้ผู้รับภายนอก (A5) ดูคลิปได้โดยไม่ต้องมีบัญชี | **must** |
| FR-5.10 | ลิงก์ภายนอกต้อง **หมดอายุตามเวลาที่กำหนด** และ **ยกเลิกก่อนกำหนดได้** | **must** |
| FR-5.11 | ลิงก์ภายนอกต้องบันทึกว่าถูกเปิดกี่ครั้ง เมื่อไร | should |
| FR-5.12 | ลิงก์ภายนอกเดาไม่ได้ และเปิดลิงก์หนึ่งต้องไม่ทำให้เห็นคลิปอื่น | **must** |

**FR-5.5 กับเงื่อนไข "ไม่ตัดต่อ":** เพดาน 60 วินาทีเป็นของแพลตฟอร์มเอง การส่งช่วงต่อเนื่อง
ช่วงเดียวที่ครอบคลุมเหตุการณ์สำคัญจึงเป็นสิ่งที่ทุกร้านทำอยู่แล้ว — สิ่งที่ห้ามคือ**ตัดต่อ

ไม่ใช่ฝากไว้กับวินัยของ CS

**FR-5.7 กับการเบิร์นตอน export:** ตัดสินใจแล้วว่าเบิร์นเฉพาะตอนส่งออก ไฟล์ที่เก็บเป็นภาพดิบ
ข้อแลกเปลี่ยนคือมีคนแย้งได้ว่า timestamp ถูกเติมทีหลัง → ชดเชยด้วย FR-7.5 (ล็อกความสมบูรณ์ของไฟล์)

### NFR-2 พื้นที่จัดเก็บ — คำนวณใหม่ตามการตัดสินใจ

ตัดสินใจแล้ว: **คงเป้า 30 วัน แล้วลด bitrate เพื่อชดเชยคลิปที่ยาวขึ้น**

การคำนวณเดิมใน design doc สมมติคลิป 60 วินาทีคงที่ ซึ่งไม่จริงแล้วตาม FR-1.6
งบพื้นที่จึงต้องกำหนดเป็น **ขนาดเฉลี่ยต่อคลิป** ไม่ใช่ความยาว

```
ดิสก์ usable                      ~790 GB
เพดานที่ยอมให้ใช้ (แจ้งเตือน 75%)   ~592 GB
÷ 30 วัน                          ~19.7 GB/วัน
÷ 1,500 ออเดอร์/วัน                ~13 MB/คลิป  ← งบต่อคลิป
```

| bitrate | ความยาวเฉลี่ยที่งบ 13 MB รองรับ |
|---|---|
| 1.5 Mbps (ค่าเดิม) | ~70 วินาที |
| 1.2 Mbps | ~87 วินาที |
| **1.0 Mbps** | **~105 วินาที** |

| # | ความต้องการ |
|---|---|
| NFR-2.1 | ขนาดเฉลี่ยต่อคลิปต้อง ≤ 13 MB เมื่อวัดเป็นค่าเฉลี่ยรายวัน |
| NFR-2.2 | ต้องยังผ่าน FR-7.1 (อ่านเลข tracking ออก) ที่ bitrate ที่เลือก — **ทดสอบด้วยตาจริงก่อนตั้งค่า** |
| NFR-2.3 | ถ้าความยาวเฉลี่ยจริงจาก pilot เกินค่าที่งบรองรับ ต้องเลือกหนึ่งใน: ลด bitrate อีก / ลด retention / เพิ่มดิสก์ — **ห้ามปล่อยให้ดิสก์เต็มแล้วค่อยตัดสินใจ** |
| NFR-2.4 | พื้นที่ของคลิปที่ pin ต้องคิดแยกและไม่นับรวมในงบ 30 วัน |

> **ความเสี่ยงที่ต้องยอมรับ:** ลด bitrate ลงเพื่อเก็บนานขึ้น = ภาพหยาบลง ซึ่งกระทบ FR-7.1
> โดยตรง ตัวแปรที่ชี้ขาดความชัดของเลข tracking คือ **โฟกัสกับแสง** มากกว่า bitrate
> (ตามที่ design doc §8 ระบุไว้) แต่มีจุดที่ลดแล้วอ่านไม่ออกแน่นอน — ต้องหาจุดนั้นใน pilot
> ไม่ใช่เดา ถ้าหาแล้วพบว่า 1.0 Mbps อ่านไม่ออก ต้องกลับมาทบทวนการตัดสินใจ 30 วัน

## 5. เรื่องราวผู้ใช้และเกณฑ์ตรวจรับ

### US-1 · A1 พนักงานแพ็ค — แพ็คหนึ่งออเดอร์

> ในฐานะพนักงานแพ็ค ฉันอยากให้ระบบอัดคลิปเองโดยฉันแทบไม่ต้องทำอะไรเพิ่ม
> เพื่อให้ยังแพ็คได้ 250 ออเดอร์ต่อวันเหมือนเดิม

**เกณฑ์ตรวจรับ**
- เมื่อสแกน IMEI แล้วกด Enter → หน้าต่างอัดขึ้นสถานะ "● กำลังอัด" ภายใน 1 วินาที
- เมื่อ API ตอบว่าไม่พบออเดอร์ → คลิปถูกทิ้ง และสถานะกลับเป็นว่าง
- เมื่อสแกนบาร์โค้ดบนกล่องที่แปะใบปะหน้าแล้ว → คลิปปิด ขึ้น ✔ และช่องรับสแกนพร้อมรับออเดอร์ถัดไปทันที
- เมื่อสแกนบาร์โค้ดของออเดอร์อื่น → ขึ้นเตือนชัดเจนภายใน 1 วินาที และคลิป**ไม่**ปิด
- เมื่อระบบวิดีโอล่ม → หน้าแพ็คทำงานปกติทุกอย่าง มีเพียงสถานะแดงบอกว่าไม่ได้บันทึก

### US-2 · A1 — บาร์โค้ดใบปะหน้าสแกนไม่ติด

> ในฐานะพนักงานแพ็ค เมื่อใบปะหน้าพิมพ์ไม่ชัดจนสแกนไม่ติด ฉันต้องปิดคลิปได้อยู่ดี

**เกณฑ์ตรวจรับ**
- มีปุ่มปิดคลิปด้วยมือบนหน้าต่างอัด กดได้ไม่เกิน 2 ครั้ง
- คลิปถูกตีตรา `manual_stop` ไม่ใช่ `unverified`
- รายงานของ A2 แยกตัวเลข `manual_stop` ออกจาก `unverified` ชัดเจน

### US-3 · A3 ทีม CS — สู้เคสลูกค้าอ้างของไม่ครบ

> ในฐานะเจ้าหน้าที่เคลม ฉันอยากได้ไฟล์วิดีโอที่อัปเข้า Shopee ได้เลย
> โดยไม่ต้องไปหาโปรแกรมตัดวิดีโอเอง

**เกณฑ์ตรวจรับ**
- เปิดหน้าเคสใน RefundCases แล้วเห็นปุ่มดูคลิปของออเดอร์นั้นเลย ไม่ต้องคัดลอกเลขไปค้นที่อื่น
- กดดาวน์โหลด → ได้ไฟล์ MP4 ที่ **≤ 60 วินาที และ ≤ 30 MB** ทุกครั้ง โดยไม่ต้องตั้งค่าอะไร
- ไฟล์ที่ได้มีวันเวลา + `ordersn` + `tracking_no` ปรากฏในภาพ
- ถ้าคลิปต้นฉบับยาวเกิน 60 วินาที → มีตัวเลือกช่วงเวลาให้เลื่อน และเลือกได้แค่ช่วงเดียวต่อเนื่อง
- อัปไฟล์ที่ได้เข้า Seller Center จริงแล้วผ่าน ไม่โดนปฏิเสธเรื่องขนาด/ความยาว/ฟอร์แมต

### US-4 · A3 — เคสที่ต้องใช้รูปนิ่ง (TikTok)

> ในฐานะเจ้าหน้าที่เคลม เมื่อ TikTok ขอ "หลักฐานการแพ็คสินค้าก่อนจัดส่ง" เป็นรูป
> ฉันอยากได้รูปจากคลิปเดียวกัน ไม่ต้องไปหาจากที่อื่น

**เกณฑ์ตรวจรับ**
- เลือกจุดในคลิปแล้วบันทึกเป็นรูปได้ ไม่เกิน 6 รูป
- แต่ละรูป ≤ 10 MB และเป็น JPG/PNG
- รูปที่ได้มีวันเวลากำกับเหมือนวิดีโอ

### US-5 · A3 — ส่งหลักฐานให้ขนส่งตอนเคลมของหาย

> ในฐานะเจ้าหน้าที่เคลม ฉันอยากส่งลิงก์ให้เจ้าหน้าที่ขนส่งดู
> โดยไม่ต้องส่งไฟล์ใหญ่ๆ ทางแชท และไม่ให้เขาเห็นคลิปอื่น

**เกณฑ์ตรวจรับ**
- สร้างลิงก์ได้จากหน้าคลิป กำหนดวันหมดอายุได้
- เปิดลิงก์แล้วดูได้ทันทีบนมือถือ ไม่ต้องล็อกอิน ไม่ต้องดาวน์โหลดก่อนดู
- ลิงก์หมดอายุแล้วเปิดไม่ได้อีก
- กดยกเลิกลิงก์แล้วเปิดไม่ได้ทันที
- ระบบบอกได้ว่าลิงก์นี้ถูกเปิดไปกี่ครั้ง เมื่อไร

### US-6 · A2 หัวหน้าคลัง — รู้ว่าโต๊ะไหนมีปัญหา

> ในฐานะหัวหน้าคลัง ฉันอยากรู้ทันทีถ้ามีโต๊ะที่แพ็คอยู่แต่ไม่ได้อัด
> ไม่ใช่มารู้ตอนสิ้นเดือนว่าคลิปหายไปสามร้อยตัว

**เกณฑ์ตรวจรับ**
- หน้าเดียวเห็นทุกโต๊ะพร้อมสถานะ
- ถ้าโต๊ะมีการพิมพ์ใบปะหน้าแต่ไม่มีตัวอัดต่ออยู่ → แจ้งเตือนภายใน 5 นาที
- รายงานรายวันบอก % `verified` รายคน

### US-7 · A4 ผู้ดูแลระบบ — ตั้งเครื่องใหม่

> ในฐานะ IT ฉันอยากตั้งเครื่องโต๊ะใหม่ให้เสร็จใน 5 นาทีโดยไม่ต้องแก้โค้ด

**เกณฑ์ตรวจรับ**
- เปิดหน้าตั้งค่า เลือกหมายเลขโต๊ะ เลือกกล้อง กดบันทึก แล้วใช้ได้เลย
- ถ้าเลือกหมายเลขโต๊ะที่ซ้ำกับเครื่องอื่นที่ออนไลน์อยู่ → ระบบไม่ยอมและบอกว่าซ้ำกับเครื่องไหน
- เปิดเครื่องวันถัดไปแล้วค่าเดิมยังอยู่

### US-8 · A3 — คลิปที่ตามหาถูกลบไปแล้ว

> ในฐานะเจ้าหน้าที่เคลม ฉันอยากรู้ความจริงว่าคลิปถูกลบตามกำหนด
> ไม่ใช่สงสัยว่าระบบพัง

**เกณฑ์ตรวจรับ**
- ค้นแล้วไม่เจอไฟล์ แต่เคยมี → แสดง "มีการบันทึกเมื่อ … และถูกลบตามนโยบาย 30 วันเมื่อ …"
- ไม่เคยมีเลย → แสดง "ไม่พบการบันทึกของออเดอร์นี้" พร้อมเหตุผลที่เป็นไปได้

## 6. เกณฑ์วัดผล Pilot (1 โต๊ะ 2 สัปดาห์)

ต้องผ่าน **ทุกข้อ** จึงจะขยายไป 6 โต๊ะ

| # | ตัวชี้วัด | เกณฑ์ผ่าน |
|---|---|---|
| P1 | สัดส่วนออเดอร์ที่มีคลิป | ≥ 98% ของออเดอร์ที่พิมพ์ใบปะหน้าที่โต๊ะนั้น |
| P2 | สัดส่วนคลิปที่ `verified` | ≥ 90% |
| P3 | อ่านเลข tracking ออกจากคลิป (สุ่ม 100 คลิป ให้คนที่ไม่รู้เลขล่วงหน้าอ่าน) | 100% |
| P4 | เห็นสินค้าชัดพอบอกรุ่น/สี (สุ่ม 100 คลิป) | ≥ 95% |
| P5 | เวลาที่เพิ่มต่อออเดอร์ | ≤ 3 วินาที ที่ p95 |
| P6 | ครั้งที่ระบบวิดีโอทำให้งานแพ็คหยุด/ช้า | 0 |
| P7 | ขนาดเฉลี่ยต่อคลิปจริง | ≤ 13 MB (ตาม NFR-2.1) |
| P8 | คลิปที่ส่งออกแล้วอัปเข้า Seller Center ผ่าน | ≥ 10 เคสจริง ไม่มีเคสที่โดนปฏิเสธเรื่องไฟล์ |
| P9 | คลิปสูญหาย | 0 |

**ข้อมูลที่ต้องเก็บระหว่าง pilot เพื่อตัดสินใจต่อ**
- การกระจายความยาวคลิป (p50 / p90 / p99) → ยืนยัน NFR-2
- จำนวนครั้งที่เตือน "ใบปะหน้าไม่ตรง" → ประเมินมูลค่า G3
- สัดส่วน `manual_stop` → บอกคุณภาพเครื่องพิมพ์ใบปะหน้า
- ปริมาณข้อมูลที่วิ่งบนเครือข่ายจริง → ปิดคำถาม design doc §10 ข้อ 1

## 9. นอกขอบเขต

- ตรวจสอบความถูกต้องของสินค้าในกล่องอัตโนมัติ (CV/AI)

- เก็บคลิปเกิน 30 วันสำหรับออเดอร์ทั่วไป
- แอปมือถือ
